Once we hit this section, we know that our intra-node scaling is not
particularly good (cmp.~Section~\ref{section:high-level:inter-node}).
The speedup as introduced from \eqref{equation:hpc-terms:speedup} is poor as we
increase the core count.
This implies (i) that we will not be able to use this code with the next
generation of machinery which will feature more cores, but it also (ii) is a
strong indicator that we leave a lot of potential compute capability unused.


Our strategy is that we briefly revise our theoretical model for this kind of
efficiency or inefficiency, respectively, before we run down an evaluation tree
to narrow down the cause of the inefficiency
(Figure~\ref{figure:core:decision-tree}).
It cannot be repeated often enough that this tree is a recommendation, not a
formalised process: 
In many cases, intuition or common sense will make you jump steps or move around
in this tree as well as in other decision trees.
The other way round, it sometimes makes sense to blend out exactly this
intuition (cmp.~assessment crime~\ref{assessmentcrime:code-expert-bias}).
