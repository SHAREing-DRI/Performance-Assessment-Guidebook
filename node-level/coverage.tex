\section{Basic theory: Amdahl's law}
\label{section:node-level:amdahls-law}

The standard code model for strong scaling experiments as we use them to assess
the single node behaviour is Amdahl's law \cite{amdahl1967}.
It assumes that the runtime of a code is given by

\begin{equation}
 \label{equation:intra-node:performance-model}
 t(p_{\text{threads}}) =
  t(1)
 \left(
 f_{\text{intra}}/p_{\text{threads}} + (1-f_{\text{intra}}) \right).
\end{equation}


\begin{figure}[htb]
 \begin{center}
  \includegraphics[width=0.7\textwidth]{node-level/strong-scaling-plot.pdf}
 \end{center}
\end{figure}

\noindent
from which it argus on the obtained speedup or efficiency,
respectively

\begin{eqnarray}
  S(p_{\text{threads}}) & = & \frac{t(1)}{t(p_{\text{threads}})} 
    \nonumber
    \\
  & = & \frac{t(1)}{t(1)
 \left(
 f_{\text{intra}}/p_{\text{threads}} + (1-f_{\text{intra}}) \right))} 
    \nonumber
    \\
  & = & \left(
 f_{\text{intra}}/p_{\text{threads}} + (1-f_{\text{intra}}) \right))^{-1}
    \label{equation:amdahl:speedup}
\end{eqnarray}

\noindent
In this model, we assume that the time $t(p_{\text{threads}})$ for a code to
finish the calculation of one fixed setup on $p_{\text{threads}}$ threads
depends only only on one variable that is specific to our code:
There is a part (fraction) $0 \leq f_{\text{intra}} \leq 1$ of the code that
benefits as we add more and more hardware threads.
It scales perfectly.
The other code fraction $1- f_{\text{intra}}$ however runs
serially and hence does not benefit from additional cores.
If we want to know how long a code fitting onto one thread would need on
$p_{\text{threads}}$ threads, we take the fraction of time that scales and
divide it by the number of threads.
After that, we add the serial part, which stays invariant.


On top of this vanilla model, we have already implicitly used an
additional penalty variable $0 < C_{\text{intra}} \leq 1$ in
Section~\ref{section:high-level:intra-node}.
It quantifies how much slower the code runs as we enable our multithreading
implementation.
It quantifies the sole parallelisation overhead.


There are a couple of issues with this model which make it often struggle to
represent real-world data:

\begin{itemize}
  \item The formula assumes that we have either sections that are parallel or
  sections that are sequential. In real codes, we often have sections that use
  some tasks or small loops. These do not scale with $p_{\text{threads}}$ which
  the model will fail to capture. 
  \item If a code is heavy on semaphores and critical sections, it will have to
  serialise some parts of the code. They cannot run in-parallel. This will lead
  to a blurred parallelism---maybe even non-deterministic.
  \item Every parallelisation induces overhead to manage threads, realise
  dependencies or synchronise parts of the code. This overhead grows as the
  number of threads grows.
\end{itemize}



\noindent
Due to these effects, many codes will yield data where the runtime starts to
raise again once we exceed a certain core count (yellow dots).
This could be modelled by an additional penalty term $C_{\text{penalty}} \cdot p_{\text{threads}} $ added to \eqref{equation:intra-node:performance-model}.
In other cases, we would have to add a noise term depending upon
$p_{\text{threads}}$.
Anyway, we note that a measured $f_{\text{intra}}$ is an effective parallel
fraction, i.e.~something we see. 
It does not mean that the code really is a simple sequence of loops which all
scale brilliantly, while the parts in-between can be accurately quantified by
$1-f_{\text{intra}}$.


Despite all of these shortcomings, we can use the model and actually turn the
argument around:
If we can use Amdahl's law \eqref{equation:amdahl:speedup} to model a code
accurately and if the resulting $f_{\text{intra}}$ is sufficiently big, then we
are on track to deliver a code which is of high intra-node efficiency.


\begin{assessmentcrime}
 Amdahl's law is used to derive statements on strong scalability without sanity
 checks if the model accurately describes the strong scaling behaviour.
\end{assessmentcrime}



\paragraph*{How it works}

\begin{itemize}[noitemsep]
  \item[$\boxplus$] Use Amdahl's formula to find out if your code follows 
  the simplistic scaling law. If so, this is good news.
\end{itemize}


\paragraph*{How it does not work}

\begin{itemize}[noitemsep]
  \item[$\boxminus$] Run a few experiments, determine $f_{\text{intra}}$ through
  regression, and draw general conclusions about your code.
\end{itemize}
