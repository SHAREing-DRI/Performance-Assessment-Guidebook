\section{Inter-node performance}
\label{section:high-level:inter-node}

\begin{summary}
 We consider a code to make efficient use of multiple nodes if it scales weakly. 
 In particular, we consider it to be scaling if it recovers from inefficiencies (efficiency drops below 80\% or 60\%) significantly whenever we increase the problem size,
 i.e.~``gets back'' to (almost) 100\% or 80\% efficiency, respectively.
\end{summary}



Inter-node behaviour means that the code runs over multiple physically separated nodes. 
In an HPC context, this almost always implies that it uses MPI.
While MPI employs a programming model which treats memory physically and logically as separate and makes them exchange data via messages,
there are (software) solutions that pretend to the code to have one large shared memory over many nodes.
Such virtually shared memory solutions would fall into this assessment category as well.
Conversely, one can use message passing, i.e.~logically separate data spaces on a single node offering one physically memory.
This would fall into the intra-node assessment rubric from Section~\ref{section:high-level:intra-node}.


Our method of choice to argue about inter-node performance is weak scaling, but we do not really (yet) dive into a proper version of Gustafson's law \cite{gustafson1988}.
Instead, we simply start from one reasonably big setup which would fit onto a single node and scale it up over multiple nodes.
This setup's parallel efficiency will go down as we increase the number of nodes, as communication overheads kick in and the work per node reduces.
Once the efficiency falls under 60\%, utilisation is really poor.
Therefore, we increase the problem size and see if we can get the efficiency up again.
The increase should lift the efficiency significantly over 80\% again. 
If it does, we end up with a zig zag pattern, where we test until we hit the 60\% threshold, increase the problem size (and hence lift the efficiency above 80\%) and then increase the node count again.
The code struggles to scale weakly, if the subsequent problem size increase improves the efficiency, but cannot push the efficiency above the 80\% efficiency threshold anymore.
The code does not scale at all, if the problem size increases fail to keep the efficiency above 60\%.



\subsection{Benchmark preparation}

For weak scaling, it is absolutely key that we first identify a performance metric that is complexity-invariant:
Let an algorithm's compute cost scale in $\mathcal{O}(f(n))$ for the problem size $n$.
If $f(n)=n$, the algorithm has linear complexity; if $f(n)=n^2$ we have quadratic complexity.
If we double $n$, the time we need for a computation on a given number of nodes $p$ should double if and only if the algorithm is linear (i.e.~$f(n)=n$).
If is quadratic, it will become four times bigger.
As we want to compare the times (and later efficiencies) over different problem sizes, we have to calibrate accordingly.

We start from the definition of speedup as $S(p) = \frac{t_1}{t_p}$, where $t_p$ is the measured time taken with $p$ nodes.

\index{Speedup}
\index{Efficiency}

The challenge is that when we want to use the efficiency formula,

\[
 E(p) = \frac{ S(p) }{ p }
  = \frac{ t_1 }{ t_p \cdot p },
\]

\noindent
for weak scaling, it contains timings determined with (potentially) two different problem sizes, but assumes that the problem size is constant; we therefore cannot compare these times directly.
If the algorithm's complexity is known, and as long as we assume that the runtime constants, i.e.~all the overheads incurred, are invariant with regards to the problem size, the calibration is easy:

\begin{equation}
 \label{equation:inter-node:efficiency}
 E(p,n)
  = \frac{ t_{1,1}/f(1) }{ t_{p,n}/f(n) \cdot p }
  \equiv \frac{t_{1}}{t_{p,n}}\cdot\frac{1}{p}\cdot\frac{f(n)}{f(1)}.
\end{equation}

\noindent
where $t_{p,n}$ is the measured time for problem size $n$ processed with $p$ nodes, and $t_1\equiv t_{1,1}$ for convenience.


\begin{assessmentcrime}
 Benchmark assessments try to argue about a code's efficiency without knowing the code's computational complexity.
\end{assessmentcrime}

\noindent
When preparing a benchmark for the inter-node, weak scaling analysis, a key point for the performance analyst is that we must have some understanding of how to scale the problem size,
i.e.~how to change the simulation problem size, but also the code's complexity $f(n)$.


\subsection{Data collection}

\subsubsection{Amending the complexity}

For some codes, the code owners can easily clarify what $f(n)$ is.
For others, the arising $f(n)$ might not be a sole polynomial.
It might also depend on factors that are difficult to fix a posteriori and need some output analysis:

Time stepping codes sometimes amend the time step size dynamically.
If the problem size changes, also the chosen time step sizes change, and we have to calibrate the timing accordingly:
In this case, we are interested in some timing per time step, i.e.~the fact that a bigger setup picks more time steps should be factored out.

Other codes employ dynamic mesh refinement.
That is, the number of compute elements changes over time.
If we increase the admissible number of elements by a factor of four, this might not necessarily lead to an exact increase of the workload by a factor of four.
Instead, we have to parse the outcome and normalise the timings by actual cells.

A final example are solvers for non-linear equation systems:
As we change the problem size, a solver might suddenly need more or fewer iterations.
We are interested in computational throughput here rather than mathematical efficiency, and hence once again have to parse the number of actual iterations and calibrate all measurements accordingly.
Due to dynamic termination criteria in the underlying linear algebra, the resulting calibration might be highly non-linear.

\subsubsection{Memory footprint}

Another consideration for weak scaling is the actual problem size:

\begin{assessmentcrime}
 We scale up the problem such that the individual work per nodes becomes very small.
\end{assessmentcrime}

\noindent
As a rule of thumb, we can simply track the memory footprint per rank and ensure that it stays within a certain regime such as 60\% of the available memory per node. 

\subsubsection{Hybrid codes}

If a code supports MPI+X with X being some kind of multithreading or has no multithreading at all, then the baseline has to be chosen such that we employ all cores of one node.
That is, the baseline $t_{1}$ might already use more than one MPI process, as long as all of these processes are pinned to the same node.

\subsubsection{Workflow}

Once we have the algorithmic complexity and memory footprints under control, we can conduct the actual measurements:

\begin{enumerate}
  \item Pick a problem size $n_1$ for one node.
  \item Measure the time $t_1 = t_{p_1,n_1}$.
  \item Increase the node count $p$ and measure the timing $t_{p,n_1}$. This is basically strong scaling in line with Section~\ref{section:high-level:intra-node}.
  \item Compute the computational efficiency on-the-fly in line with \eqref{equation:inter-node:efficiency}.
  \item If the efficiency $E(p, n)\leq 60\%$, use a larger problem size $n$ and continue the measurements of $t_{p,n}$ from hereon with the increased problem size.
\end{enumerate}

\noindent
The recipe leaves it open by how much we should increase $n$ every time.
A rule of thumb is that we maximise the value such that the nodes still can handle the problem, and, at the same time, try to ensure that each compute node hosts local subproblems with roughly the same memory footprint that we obtained for $n_1$ on one node.



\subsection{Evaluation}

Our roadmap to determine how good the distributed-memory behaviour is, i.e.~our strategy to come up with a single number, is straightforward.
First, we record all the $p$ for which we had to increase the problem size into a set $\mathbb{C}_{\text{critical}}^{\text{60\%}}$.
For these problem sizes, we only pick the timings/efficiencies for the bigger setup, i.e.~after we have increased the problem size.

\begin{performancemetric}
 We evaluate 
 \begin{eqnarray*} 
  C_{\text{inter}}^{\text{80\%}} = | \{
    p \in \mathbb{C}_{\text{critical}}^{\text{60\%}}: \quad
    E(p, n) \geq 80\%
    \}
  |
  \qquad
  \text{and} \\
  C_{\text{inter}}^{\text{60\%}} = | \{
    p \in \mathbb{C}_{\text{critical}}^{\text{60\%}}: \quad
    80\% \geq E(p, n) \geq 60\%
    \}
  |,
 \end{eqnarray*}
 \noindent
 to evaluate to which degree the efficiency curve remains above $60\%$ or within the corridor of $60\%-80\%$.
\end{performancemetric}

If all jumps remain above 60\% with the majority above 80\%, the scalability is very good.
If most jumps remain above 60\%, the scalability is acceptable.

\paragraph*{How it works}

\begin{itemize}[noitemsep]
  \item[$\boxplus$] Run the code over an increasing number of nodes and increase the problem size every time the efficiency becomes inacceptably low.
  \item[$\boxplus$] Study if these problem size increases help you to push the efficiency up significantly.
\end{itemize}


\paragraph*{How it does not work}

\begin{itemize}[noitemsep]
  \item[$\boxminus$] Run the same problem size over a few  different node counts and make statements on the code's behaviour. 
  \item[$\boxminus$] Rely on raw timings that do not take the computational workload per setting into account. 
\end{itemize}
