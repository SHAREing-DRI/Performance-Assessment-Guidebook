\section{Wrap-up}
\label{section:high-level:wrap-up}


\begin{summary}
 Interpreting high-level assessment outcomes requires input from code and domain experts.
\end{summary}


Any high-level analysis should be wrapped up and summarised by the assessor. 
Producing visual artefacts helps to convey key insights effectively. 
However, this summary must be written and shared with care.

The outcome metrics are objective in the sense that they represent observed code behaviour.
There is no room for evaluation or contextualisation. 
In particular, claims of code exceptionalism must be challenged directly:

If developers argue that their code is so complex and specialised that poor performance on certain metrics is natural and expected ``for this particular field'', that claim can be noted but must not influence the assessment or its publication. 
The assessment reflects the state of the code. 
If developers instead argue that the code behaves differently in practice, this reveals that they have failed to provide a characteristic, meaningful benchmark---not that the assessment is wrong. 
In both cases, such pushback is a warning sign and grounds to consider terminating the assessment process.

The situation is different when it comes to correlating and weighting the five high-level metrics. 
When the high-level assessment is used to prioritise follow-up studies, the assessor must consult code and domain experts to determine where to focus. 
A code exhibiting both poor core performance and poor I/O behaviour does not necessarily warrant tackling both issues: 
the code community is best placed to judge which flaw has the greater impact on their science. 
The metrics presented in this chapter carry no relative weighting against one another.

Domain experts may also identify correlations between metrics. 
Poor intra-node load balancing, for instance, will often lead to poor average core utilisation as a direct consequence. 
An expert can recognise such dependencies and rightly argue that follow-up work should target the balancing issue first. 
This matters especially because the high-level assessment treats the code as a single block, without distinguishing between individual execution phases. 
Domain experts are therefore well placed to clarify why certain flaws become particularly significant at scale---for example, in larger runs or longer calculations.
