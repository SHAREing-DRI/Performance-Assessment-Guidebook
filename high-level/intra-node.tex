\section{Intra-node (node-level) performance}


On an individual node, our first goal has to be that we use all the hardware threads efficiently.
Some people prefer the term cores of threads.
The term intra-node hence means all those cores sharing one memory.
Hereby it does not matter if we have a code using MPI or a genuine multithreading language:
We assess the runtime characteristics for a code physically sharing its memory.
It might be written logically in a distributed memory fashion.


Our method of choice to argue about node-level performance is strong scaling.
We apply a slight variation of Amdahl's law \cite{xxx}:
We assume that the runtime of a code is given by

\begin{equation}
 \label{equation:intra-node:performance-model}
 t(p_{\text{threads}}) = \frac{t_{\text{serial}}}{C_{\text{intra}}}\left( f_{\text{intra}}/p_{\text{threads}} + (1-f_{\text{intra}}) \right).
\end{equation}


\noindent
In this model, we assume that the time $t(p_{\text{threads}})$ for a code to finish the calculation of one fixed setup on $p_{\text{threads}}$ threads depends only only on a few variables that are specific to our code:
First, there is a penalty variable $0 < C_{\text{intra}} \leq 1$.
It quantifies how much slower the code runs as we enable our multithreading implementation:
\[
 t(1) = \frac{t_{\text{serial}}}{C_{\text{intra}}}.
\]

\noindent
Beyond that, we have a part $0 \leq f_{\text{intra}} \leq 1$ of the code that benefit as we add more and more hardware threads.
The other code fraction $1- f_{\text{intra}}$ however runs serially---representing non-parallelised code sections or the serialisation arising from atomics, critical sections and semaphores---and hence does not benefit from additional cores.
The whole model is a variation of the vanilla strong scaling law due to Amdahl \cite{xxxx} which corresponds to the special case $C_{\text{intra}}=1$.


\paragraph{Benchmark preparation}

Throughout this assessment, we use one fixed problem setup.
The setup has to be chosen such that we can compute it on a single core if necessary.
However, it also has to be reasonably big such that it makes sense to exploit all threads of a node.


\begin{assessmentcrime}
 We start an intra-node assessment with a code which only uses a tiny fraction of the main memory.
\end{assessmentcrime}

\noindent
We may assume that a node and its memory are somehow balanced.
If we don't use a reasonable amount of this memory for a test run, then there is simply not enough work to do to utilise all cores.
We can barely blame the code.
As a rule of thumb, we should have a memory footprint which is at least 20\% of the total RAM available on the whole node.


\paragraph{Data collection}

For the data collection, we first time the simulation without any parallelisation, which is, trivially, a single-core run.  
We then switch to the parallel code version and vary the core count $p_{\text{intra}}$. 
In OpenMP, we can simply set \texttt{OMP\_NUM\_THREADS} to achieve this.
Other tasking frameworks might require us to change the thread count in the Slurm script, or to set some other OS parameters. 
If that does not work, you can always use

\begin{verbatim}
taskset -c 0-3 ./myexec
\end{verbatim}

\noindent
to use the first four cores only, e.g.
If we have a code base which employs MPI only, we set the number of ranks per node accordingly.

From the set of measurements (Figure~\ref{figure:intra-node}), we first compare the two timing for a single core (the red dot vs.~the green dot above it) and compute the $C_{\text{intra}}$.
After that, we can determine $f_{\text{intra}}$ for each and every measurement due to \eqref{equation:intra-node:performance-model}
or simply use regression over all data points.


Many codes will yield data where the runtime starts to raise again once we exceed a certain core count (yellow dots).
This could be modelled by an additional penalty term $C_{\text{penalty}} \cdot p_{\text{threads}} $ added to \eqref{equation:intra-node:performance-model}.
However, in many cases that's too much of an effort: 
In many cases, the parallel efficiency $f_{\text{intra}}$ will already cause the scaling to deteriorate way before this penalty kicks in, i.e.~before we see it visually.
In this case, it is perfectly reasonable to constrain the maximum $p_{\text{threads}}$ such that the we do not run into the ``problematic'' range of threads and to neglect the measurements further on.
The performance flaws will already be documented in this case.


For hybrid MPI+X codes, we have a certain freedom:
We can use an arbitrary number of MPI ranks---indeed our analysis also works for pure MPI codes as long as we stick to one node---and use threads on top such that we exploit all $p_{\text{threads}}$ hardware threads of interest.
This means, we have a certain degree of freedom.
Picking one rank and four threads is, logically, equivalent to picking two ranks and two threads each.
It is part of the assessment to play around with these degrees of freedom.
Once again: If we spot sudden runtime jumps (yellow dots in example sketch) and if these jumps coincide with a NUMA domain or socket, then this might be a strong indicator that we should use MPI instead of threading.
However, one might argue that this is already part of an in-depth analysis rather than a high-level overview.


\paragraph{Evaluation}

We use the two quantities $C_{\text{intra}}$ and $f_{\text{intra}}$ to determine if we consider the code to have an intra-node flaw:

\begin{center}
 \begin{tabular}{r|p{0.22\textwidth}p{0.22\textwidth}p{0.22\textwidth}}
  & $C_{\text{intra}}\geq 0.8$ & $0.8 > C_{\text{intra}}\geq 0.6$ & $0.6 > C_{\text{intra}}$ \\
  \hline
  $f_{\text{intra}} \geq 0.8$
   & \cellcolor{green!25} perfect
   & \cellcolor{orange!25}
   & \cellcolor{red!25}
  \\
  $0.8 > f_{\text{intra}} \geq 0.6$
   & \cellcolor{orange!25}
   & \cellcolor{orange!25} flaw
   & \cellcolor{red!25}
  \\
  $0.6 > f_{\text{intra}}$
   & \cellcolor{red!25}
   & \cellcolor{red!25}
   & \cellcolor{red!25} severe flaw
 \end{tabular}
\end{center}

%{equation:intra-node:performance-model}

\begin{performancemetric}
 If $C_{\text{intra}}< 0.8$, the implementation introduces a significant overhead for the multithreading.
 If $C_{\text{intra}}< 0.6$, the overhead is severe.
\end{performancemetric}


\begin{performancemetric}
 If $f_{\text{intra}}< 0.8$, the code does not scale particularly well over the threads.
 If $f_{\text{intra}}< 0.6$, the scaling is severely poor.
\end{performancemetric}


\noindent
A massive overhead requires us to look into profiles next.
Poor scaling implies that we should look into a trace over the node.

\paragraph*{How it works}

\begin{itemize}[noitemsep]
  \item[$\boxplus$] Compile your code without multithreading/parallel support and compare its performance to a code without any parallelisation to determine the overhead of the parallel implementation.
  \item[$\boxplus$] Run a strong scaling study and calibrate the constants of an extended Amdahl model against these measurements. 
\end{itemize}


\paragraph*{How it does not work}

\begin{itemize}[noitemsep]
  \item[$\boxminus$] Skip intra-node scalability studies, as the code is ``only'' MPI.
  \item[$\boxminus$] Perform a sole strong scalability study without taking the implementation penalty into account.
\end{itemize}
