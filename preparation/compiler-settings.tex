\section{Compiler setup}
\label{section:preparation:compiler-settings}

When worrying about optimisation, many modern compilers can leverage significant optimisations for us. Likely, performance analysts will receive codes that specificy build instructions that include a variety of compiler flags with some level of optimisations. It may be the case that the build instructions are old and so we could exploit further optimisations.

At this stage, we keep things simple. We simply observe what we have received, either through a submission or through code documentation, and note it down. This is a crucial stage, because at this point we really see whether we are able to follow the code owners' instructions and reproducibly build the benchmark. One thing which should stand out at this stage is what parallelism is included in the build process. Are we using OpenMP flags? Are there flags for targeting device architectures for GPUs? We take note of these as these will be relevant later in the assessment.
We will go into more details about compiler optimisations in Section~\ref{section:core:compiler-optimisations}. 

One thing we we might want to include at this stage are debug symbols.
These instruct the compiler to insert additional information into the source
code which tools can then later use to draw inference
from, e.g.~which source code line a certain instruction stems from.
Usually, you cannot know from a single instruction in a machine code, where this
comes from in the original code.
With the debug systems, we inject exactly this information into the executable.
Therefore, we should add \texttt{-g}.
Some compilers support more detailed information (e.g.~using \texttt{-g3}).
It requires studying the compiler's feedback whether these flags disable
optimisations, in which case we might have to balance insight vs.~best-case
speed. Often profilers require debug symbols to allow them to relate machine code to source which help when digging into the performance of the generated machine code.

\begin{checklist}
 \item Your benchmark is compiled with debug symbols (\texttt{-g}).
\end{checklist}


\paragraph*{How it works}

\begin{itemize}[noitemsep]
  \item[$\boxplus$] Follow the proposed build instructions and document them, noting anything that faults.
  \item[$\boxplus$] Ensure to document flags that relate to the parallelism, such as OpenMP flags.
\end{itemize}

\paragraph*{How it does not work}

\begin{itemize}[noitemsep]
  \item[$\boxminus$] Take the build instructions and then aim to implement further compiler optimisations.
\end{itemize}
